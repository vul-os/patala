# Go binding

`patala-go` is a Go package generated by
[`uniffi-bindgen-go`](https://github.com/NordSecurity/uniffi-bindgen-go) from
the **same** `#[uniffi::export]` surface the Python binding uses. It contains
no Rust crate of its own and reimplements nothing — not `PatalaRail`, not
`RailClass`, not `RailCapabilities`, not `Quote`, not `Receipt`. It reads the
UniFFI metadata embedded in the compiled cdylib and emits Go from it.

That is [M×1, never M×N](polyglot.md) in its most literal form.

## Read this before you reach for it

**This binding uses cgo.** If your Go project needs a pure-static,
trivially-cross-compiled binary, use [the sidecar](sidecar.md) instead. That is
not a caveat at the bottom of this page — it is the main thing to know before
choosing this path, and it is the choice `cackle`, the first real Go consumer
in this suite, actually made.

### The cgo cost

The generated file contains `import "C"` and hand-written cgo glue calling
into the UniFFI C-ABI scaffolding compiled into the cdylib. Concretely:

- **`CGO_ENABLED=1` is mandatory.** Verified, not assumed: with
  `CGO_ENABLED=0`, `go build ./...` fails with
  `build constraints exclude all Go files in .../bindings/patala`.
- **A C toolchain is required at build time** — whatever `cgo` shells out to
  on your platform. A CI image that installs only Go now needs a compiler.
- **Your binary stops being a self-contained static executable.** It links
  dynamically against the cdylib. On macOS, `otool -L` on the built example
  shows an `LC_LOAD_DYLIB` entry pointing at the library's **build-time
  absolute path** — Rust's default dylib install name is not rpath-relative.
  The library has to travel with the binary, or the install name has to be
  fixed up with `install_name_tool`/`-rpath`, or `LD_LIBRARY_PATH` /
  `DYLD_LIBRARY_PATH` has to be set — on every machine it runs on, matching
  that machine's OS and arch.
- **Cross-compilation gets much harder.** `GOOS=linux GOARCH=arm64 go build`
  from a macOS host, which just works for pure Go, now needs a matching cross
  C toolchain *and* a cdylib built for that target triple. This is exactly the
  pain `CGO_ENABLED=0` exists to avoid.
- **Builds get slower and more fragile.** cgo compilation is slower than pure
  Go and adds Cargo's failure modes to your Go build: if the cdylib is not
  built and on the linker's search path, `go build` fails at the link step
  with a linker error rather than a Go-shaped one.

What you get in exchange is native Go types, an in-process call instead of a
socket round trip, and access to every rail the cdylib was built with — which
the sidecar cannot offer today. [Choosing a mode](choosing-a-mode.md) lays the
two side by side.

## Build and run

Every step is a `make` target in `patala-go/`, and the Makefile is the one
place the cdylib's filename and linker flags are written down — use it rather
than retyping them:

```bash
cd patala-go

make run-example   # generate bindings, then run examples/roundtrip
make build         # generate bindings, then go build ./...
make test          # generate bindings, then the gated go test ./...
```

Those three build a **MockRail-only** cdylib. To get the fiat surface as well:

```bash
make run-example-fiat            # FEATURES=fiat-all, then the fiat example
make test-fiat                   # FEATURES=fiat-all, then the gated fiat suite
make FEATURES=fiat-stripe,fiat-paystack generate   # or any narrower set
```

The one prerequisite `make` will not install for you is the generator itself,
and its version must match the workspace's `uniffi` pin exactly — a mismatched
bindgen can fail against the metadata the cdylib actually embeds:

```bash
cargo install --locked --git https://github.com/NordSecurity/uniffi-bindgen-go \
    --tag v0.5.0+v0.29.5 uniffi-bindgen-go
```

Do **not** install it without `--tag`: the default branch targets a newer
`uniffi-rs` than this workspace pins. `make check-uniffi-bindgen-go` verifies
the binary is on `PATH` and prints that command if it is missing. It is a Rust
binary installed with `cargo install`, not `go install`, even though what it
emits is Go.

`patala-go/bindings/` is gitignored — like `target/`, it is build output.

## A round trip

```go
import patala "github.com/vul-os/patala/patala-go/bindings/patala"

rail := patala.PatalaRailNewMock(
    "mock", patala.RailClassNonCustodialFinal, []string{"USDC"}, 0, false,
)

req := patala.PayRequest{
    AmountMinor: 1_250, // uint64, never a float
    Currency:    "USDC",
    Destination: "dest-anything",
    Reference:   "order-1",
}

receipt := must(rail.Charge(req))
valid := must(rail.Verify(receipt)) // fail-closed: a tampered receipt verifies false
```

Adapted from `patala-go/examples/roundtrip/main.go`.

## What is exposed

- **`PatalaRail`** — the one type Go code touches: `Id()`, `Capabilities()`,
  `Quote()`, `Charge()`, `Verify()`, `VerifyWebhook()`,
  `ValidateDestination()`.
- **`RailClass`** and **`Settlement`** — mirrored 1:1 from the core, never
  flattened.
- **`RailCapabilities`, `PayRequest`, `Quote`, `Receipt`** — generated Go
  structs. Amounts stay `uint64` minor units, never a float.
- **`PatalaError`** — a Go error type per core error variant (`Unsupported`,
  `Rail`, `InvalidRequest`, `CrossClassFailover`, `AllRailsFailed`). `Verify`
  failing closed is still `(false, nil)`, never an error — the same contract
  as the trait and the Python binding.
- **`PatalaRailNewMock`** and
  **`PatalaRailNewMockWithoutDestinationChecks`** — always available. The
  second answers `Unknown` for every destination, so the fiat-shaped "a human
  must decide" branch of a payout UI is testable from Go in the feature-free
  build.
- **`PatalaRailNewFiat(provider string, config map[string]string)`** and
  **`PatalaFiatProviders() []string`** — present only in bindings generated
  from a cdylib built with the fiat features.
- **`DestinationStatus` / `DestinationVerdict`** — five variants, never a
  bool. The verdict carries `Reason`, `HumanMustConfirm` (**true on every
  verdict**), `ExchangeDepositCaveat` and `IsRefusal`. `IsRefusal` is a field,
  not something to derive from `Status`, because a `switch` that has not heard
  of a status added later falls through to "not a refusal" — failing open.
  `ValidateDestination` returns no error: "I cannot check" is the `Unknown`
  verdict.
- **`ExchangeDepositCaveat() string`** — the same caveat text every verdict
  carries, for the form where a customer is first asked for a payout address.

When a real rail grows a constructor in the Rust UniFFI surface, it becomes
reachable here the next time bindings are regenerated. No redesign.

## The fiat surface, and the build tag

```go
rail, err := patala.PatalaRailNewFiat("manual", map[string]string{})

// or, once fiat-stripe is compiled in:
rail, err := patala.PatalaRailNewFiat("stripe", map[string]string{
    "secret_key":     "sk_live_...",
    "webhook_secret": "whsec_...",
})
```

`config` keys are the same field names the
[per-provider table](rails-fiat.md#config-keys-by-provider) documents — they
come from the same Rust surface, so there is nothing Go-specific to relearn.
Every value is a string, even numeric and boolean ones:
`"settlement_days": "2"`, `"requires_kyc": "true"`. An unknown provider, or one
whose Cargo feature was not compiled in, returns a Go `error` wrapping
`PatalaError.InvalidRequest` — never a panic.

**Why a Go build tag as well as a Cargo feature.** Go has no per-dependency
optional-feature mechanism, so `examples/fiatroundtrip/main.go` carries a
`//go:build fiat` constraint. Without `-tags fiat`, `go build ./...` and
`go test ./...` skip it entirely — which is what keeps the plain `make build`,
`make test` and `make run-example` targets working unchanged against a
MockRail-only cdylib. Only the `-fiat` targets pass the tag.

## Webhooks

`VerifyWebhook` is on the trait and therefore in these bindings. Forward the
processor's request verbatim: `RawBody` as the raw `[]byte` read off
`*http.Request` **before** any JSON decode, `Headers` as the request's
headers, `Query` only for schemes whose secret rides in the URL (LNbits), and
`NowUnix` as the current time so replay windows are checked against an
explicit clock.

A returned `WebhookEvent` means the rail authenticated the delivery. A non-nil
error means it did not. `WebhookStatusUnconfirmed` means
genuine-but-says-nothing-about-money: look up your own record for `ObjectId`
and call `Verify`.

Before the trait carried this, webhook verification existed only as
provider-specific Rust free functions, which UniFFI cannot see — so a Go
consumer could confirm a payment **only** by polling `Verify`. That gap is
closed.

### Why the `WebhookStatus` pinning is the important part

`WebhookStatus` crosses the FFI as a bare integer: UniFFI lowers enum variants
to their ordinal position (`Settled` = 1, `NotSettled` = 2, `Unconfirmed` = 3).
Nothing at runtime names the Rust variant a value came from. Reorder the Rust
enum, regenerate, and every Go call site still compiles and means something
different.

`Unconfirmed` is **never** payment. If it ever arrived carrying `Settled`'s
number, a consumer would mark unpaid orders paid — and `cackle` consumes these
bindings, so that is a money bug, not a hypothetical.

Three layers pin it, because no single layer catches everything: constant
assertions catch renumbering; a scan of the generated source catches an added
or removed variant, which renumbering assertions cannot see; and live
round-trips against genuinely signed deliveries catch a rail mapping its own
outcome to the wrong variant, which neither static check can see.

## A test target that fails when there are no tests

`bindingtest/` is this module's suite: real `testing.T` tests against the
generated bindings, exercising exactly what a downstream consumer sees.

Before it existed, `make test` ran `go test ./...` over a module with no
`_test.go` files anywhere. `go test` prints `[no test files]` and **exits 0**
in that situation, so the target reported success having executed zero
assertions. Adding tests alone would not have fixed that — tests can be
deleted, excluded by a build tag, or filtered out by a stray `-run`.

So every `go test` invocation runs through `scripts/go-test-gate.sh`, which
fails when `go test` fails, when **zero tests ran** (printing the packages that
had none), when fewer than a floor of top-level tests passed, or when a
**required** test — named in the Makefile, the money-critical ones — did not
run *and* pass. There is no skip path: an inconclusive run never exits 0.

| File | Build tag | What it pins |
|---|---|---|
| `binding_test.go` | — | the mock constructor, `Id`, `Capabilities`, `Quote`/`Charge`/`Verify`, fail-closed verify against four kinds of tampering, `RailClass` discriminants, the typed error variants, `VerifyWebhook` reporting `Unsupported` where there is no push delivery |
| `webhook_status_test.go` | — | every `WebhookStatus` wire value, that **only** `Settled` may be read as payment, that the zero value is not payment, and that the variant set is exactly the three known ones |
| `fiat_webhook_test.go` | `fiat` | the by-name fiat constructor, provider coverage against `patala-fiat/src/`, and `VerifyWebhook` against genuinely signed Stripe and BTCPay deliveries, plus five fail-closed cases per scheme |
| `destination_test.go` | — | all five `DestinationStatus` variants arriving as five **distinct** values, discriminants pinned, `HumanMustConfirm` true on every verdict, the caveat present and identical to the free function, `IsRefusal` crossing as data, purity across 25 calls, and the whole compensating-payment flow walked end to end from Go |
| `destination_fiat_test.go` | `fiat` | that **real** fiat rails answer `Unknown` rather than claiming a check they cannot perform, and that a blank destination is still a `Malformed` refusal |

**This runs in CI.** The `go-binding` job installs `uniffi-bindgen-go` at the
pinned tag, then runs `make smoke-go`, which is `make test-fiat` + `make test`
plus a `gofmt` check. The two prerequisites that used to justify running it by
hand — a pinned bindgen and a C toolchain — are a cached `cargo install` and a
compiler the runner already ships. Go is the language of the first real
consumer, which made it a poor choice for the one binding no gate covered.

## What has actually been executed

Real output from a genuine call through cgo into the compiled Rust cdylib:

```text
capabilities OK: class=2 currencies=[USDC USD] holds_funds=false
quote OK: total_minor=1250 (uint64, not float)
charge OK: receipt rail_id="mock" amount_minor=1250
verify OK: genuine receipt verified true
verify OK: tampered receipt verified false (fail-closed)
error mapping OK: unsupported currency raised PatalaError: InvalidRequest: Message=rail mock does not support currency EUR

ALL GO ROUNDTRIP ASSERTIONS PASSED
```

(`class=2` is the non-custodial-final discriminant — UniFFI Go enums are
integer-backed and print numerically under `%v` unless a caller adds a
`String()` method. Not a bug, just Go's default enum printing.)

And with the fiat surface compiled in:
